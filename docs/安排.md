## 二、W1–W4 逐 Session（实战代码增强版）

### W1（09-21 ~ 09-27）· 交互底座与流式对话

> 深入点：**上下文多大时模型开始答不准（Token 压力测试）**。S3 的代码实验就是深入点本身。

#### S1（周一晚 · 1.5h）
- **核心代码任务**：
  1. 搭建 conda 环境与项目骨架，安装核心依赖（`langchain-core`、`langchain-deepseek`、`python-dotenv` 等）
  2. 调通 DeepSeek API 连接
  3. **【代码增量】** 实现 `stream_ask()` 生成器支持打字机式流式输出
  4. **【代码增量】** 实现基于控制台的交互式 CLI 循环（支持连续提问与简易上下文）
- **交付物**：`src/code_agent/core/model.py`、`src/code_agent/cli.py`（可交互流式 CLI）

#### S2（周三晚 · 1.5h）
- **核心代码任务**：
  1. 定义清晰的模型抽象层（`ChatModel` 协议/基类），使业务调用解耦
  2. 接入 `loguru`，记录每次调用的输入/输出 Token 数与响应耗时
  3. **【代码增量】** 使用 Pydantic 定义代码评审数据模型（`ReviewIssue`、`ReviewReport`）
  4. **【代码增量】** 编写代码审查 System Prompt，让模型按结构化 JSON 返回问题行号与建议
- **交付物**：模型抽象模块 + Pydantic 结构化输出模块 + 带耗时统计的日志

#### S3（周五晚 · 1.5h）
- **核心代码任务**：
  1. 编写实验脚本 `test_context_limit.py`
  2. 手动构造不同大小的代码上下文（从 100 行、500 行递增到 2000 行），要求模型“指出第 X 行的变量名”
  3. 记录不同 Token 长度下的响应耗时与幻觉拐点，数据记入极简笔记
- **交付物**：`tests/test_context_limit.py` + 一份上下文失效点测试数据

#### W（周末整块 · 5h）
- **核心代码任务**：
  1. 安装 `rank_bm25`，编写最朴素的代码仓库索引器（遍历源文件 $\to$ 分词 $\to$ 构建倒排）
  2. 在 CLI 中支持命令：`search <关键词>`，打印出命中度最高的前 3 个代码片段与行号
  3. 准备 5 条针对自己代码库的测试提问，验证关键词检索效果
- **交付物**：`src/code_agent/index/bm25_index.py` + CLI 关键词搜索功能可用

**验收标准**：在终端输入问题，CLI 能即时通过 BM25 查出代码片段，并流式给出带行号的回答。

### W2（09-28 ~ 10-04）· 出处与记账

> 深入点：**不校验引用会发生什么（亲手抓出模型的幻觉出处）**。

#### S1（周一晚 · 1.5h）
- **核心代码任务**：
  1. 强化 Prompt 约束：答案中每个结论必须附带 `[file_path:start_line-end_line]`；给不出依据时必须显式输出“无依据”，严禁推测
  2. 编写正则解析器，从模型回答的 Markdown 文本中自动提取所有文件路径与行号
- **交付物**：`src/code_agent/core/citation.py`（引用解析模块）

#### S2（周三晚 · 1.5h）
- **核心代码任务**：
  1. 编写**引用自动校验器**（`validate_citation`）：用 Python 检查引用的文件是否真实存在、行号是否在文件范围内
  2. 故意提几个仓库里不存在的函数名，观察模型是否编造了假行号，并验证校验器能成功报警
- **交付物**：引用有效性自动化校验函数 + 单元测试

#### S3（周五晚 · 1.5h）
- **核心代码任务**：
  1. 收集并固化 10 条真实测试用例到 `eval/cases/`（覆盖：符号位置查找 4 条、逻辑行为分析 4 条、不存在的虚构功能 2 条）
  2. 编写批量跑用例的初版 Python 脚本
- **交付物**：10 个 YAML/JSON 测试案例文件

#### W（周末整块 · 5h）
- **核心代码任务**：
  1. 运行批量脚本跑完这 10 个案例，统计：完成率、引用存在率（真实存在行号占比）
  2. 记录当前纯关键词检索下的第一份**基线准确率数字**（如：引用准确率 50%）
- **交付物**：`eval/runs/baseline_bm25.json`（第一个基线数据）

**验收标准**：能拿出一份真实的数字跑分，说明当前纯关键词检索的引用准确率是多少。

### W3（10-05 ~ 10-11）· 自动化评测工具化

> 深入点：**什么样的问题适合用来评测 Agent（区分真实卡点与简单送分题）**。

#### S1（周一晚 · 1.5h）

  1. 将案例扩充至 25~30 条（加入跨函数逻辑关联、异常处理查找等）

- **交付物**：`eval/cases/` 扩展至 30 条规范化用例

#### S2（周三晚 · 1.5h）
- **核心代码任务**：
  1. 编写独立的自动化评测执行器 `eval/run_eval.py`
  2. 脚本支持：加载 cases $\to$ 并发或循环调 CLI $\to$ 解析引用 $\to$ 校验文件与符号命中 $\to$ 计算指标
- **交付物**：`eval/run_eval.py` 完整评测运行器

#### S3（周五晚 · 1.5h）
- **核心代码任务**：
  1. 完善报告输出格式：直接输出 Markdown 表格或控制台高亮报告
  2. 收集关键运行指标：引用有效率、关键文件召回率、单次问答平均 Token、单次平均耗时

#### W（周末整块 · 5h）

- **交付物**：正式运行评测报告 + 失败用例原因归类

**验收标准**：在终端敲入 `python eval/run_eval.py`，30 秒后自动吐出带准确率与 Token 消耗的详细评测报告。

## 三、W5–W16 逐周规划（代码实战演进）

### 阶段三：混合检索与多数据源（W5 ~ W7）

* **W5 · 向量与混合检索**：
  * **代码任务**：利用标准库 `ast` 编写 Python 代码切块器（按 Class 和 Function 边界切分，保留函数签名与完整上下文）；接入本地轻量向量库（ChromaDB 或 LanceDB，免 Docker 极简部署）；实现 BM25 + 向量相似度加权混合检索（Hybrid Search）。
  * **交付物**：`src/code_agent/index/ast_chunker.py` + 混合检索器实现 + 跑分报告对比。
* **W6 · 接入 Markdown 技术资料源**：
  * **代码任务**：编写 Markdown 文档解析器（按二级/三级标题层级切块）；为每个文档块打上元数据（`source_type="doc"`, `file_path`, `title`）；将技术规范文档纳入索引。
  * **交付物**：支持同时索引“源码仓库”与“规范文档”的双源索引层。
* **W7 · 多源召回与融合**：
  * **代码任务**：实现互惠排名融合（RRF，Reciprocal Rank Fusion）算法，抹平向量距离与 BM25 分数尺度差异；答案中明确标注信息来自“代码事实”还是“设计规范”。
  * **交付物**：跨数据源融合排序器 + 自动化评测命中率对比。

### 阶段四：检索工具化与自主探查循环（W8 ~ W10）

* **W8 · 检索工具化（Tool Binding）**：
  * **代码任务**：将检索逻辑包装为标准 LangChain Tool（`search_code_symbols`、`read_file_snippet`、`lookup_doc`）；编写清晰严密的工具描述（Docstring与参数说明）；使用 `.bind_tools()` 绑定至 DeepSeek 模型。
  * **交付物**：可供模型调用的原生代码探查工具集。
* **W9 · 手写 ReAct 执行循环与容错**：
  * **代码任务**：不依赖黑盒框架，手写 `while True` 的 ReAct 执行循环（模型输出 ToolCall $\to$ 本地反射调用 $\to$ 注入 ToolMessage $\to$ 循环直至给出最终回答）；加入**最大循环步数（Max Steps）熔断**与异常安全捕获。
  * **交付物**：自主多步探查的代码助手原型 + 具备防死循环能力的执行引擎。
* **W10 · Git 历史源接入（三源取证）**：
  * **代码任务**：通过 `GitPython` 或系统命令增加 `query_git_history` 工具（查询某函数或文件的最近 commit message 与修改记录）；测试助手能否回答“这段代码为什么在 3 天前修改了超时时间”。
  * **交付物**：代码 + 文档 + Git 历史三源联动探查能力。

### 阶段五：上下文工程与记忆治理（W11 ~ W12）

* **W11 · 上下文治理与 Token 预算**：
  * **代码任务**：建立单次会话的上下文预算管理器（为系统提示词、检索结果、历史对话、工具返回分配固定 Token 比例）；实现历史消息滑动窗口裁剪与压缩摘要；对大段工具输出进行智能截断，避免爆窗口。
  * **交付物**：`src/code_agent/core/context_manager.py`（上下文预算管理器）。
* **W12 · 记忆分层与经验沉淀**：
  * **代码任务**：设计双层记忆结构：短期工作记忆（当前任务上下文）+ 长期项目偏好记忆（存储在本地 SQLite 中的编码规约与常见坑）；实现“评审经验反哺”（当用户纠正了某个评审意见时，自动写入本地规则库）。
  * **交付物**：基于 SQLite 的项目级规则记忆持久化模块。

### 阶段六：LangGraph 状态机重构与工程落地（W13 ~ W16）

* **W13 · LangGraph 状态机编排 ★核心跃迁**：
  * **代码任务**：将之前的手写 while 循环正式重构为 LangGraph 的 `StateGraph`；定义清晰的 `AgentState`；构建独立节点：`PlanNode`（意图拆解）、`RetrieveNode`（查代码/文档）、`ReviewNode`（审查代码）、`JudgeNode`（判定是否需要补充信息）；配置条件边（Conditional Edges）。
  * **交付物**：结构清晰、可视化友好的 LangGraph 代码审查工作流。
* **W14 · 中断恢复与人机协同（Human-in-the-loop）**：
  * **代码任务**：接入 LangGraph 的 `MemorySaver` / SQLite Checkpointer 实现状态断点保存；在助手准备生成修复补丁或修改本地代码前，通过 `interrupt()` 触发挂起，等待终端用户确认 `[Y/N]` 后继续执行。
  * **交付物**：具备断点记忆与审批机制的安全执行流程。
* **W15 · 代码与规范一致性审计**：
  * **代码任务**：实现自动化的一致性审查逻辑：抽取文档中的规则（如“超时必须是 30s”）与代码中的实际常量（如 `TIMEOUT = 10`）进行交叉比对，自动输出“文档与代码不一致清单”。
  * **交付物**：自动化一致性审查子图。
* **W16 · 收口与工程展示**：
  * **代码任务**：编写 CLI 一键命令（如 `code-agent review ./src`）；完善全链路日志追踪（可复现每次审查的模型推理与工具调用轨迹）；代码整体规范化与打包测试。
  * **交付物**：一个真正能日常使用、具备代码检索与深度评审能力的个人工程助手。

## 四、日常极简工作流（清爽编码模式）

放弃繁重的便签仪式与打卡模板，每次坐下只需执行三步：

1. **坐下即写（2 分钟）**：
   - 打开对应 Session 的代码任务，明确今天增加哪一个类或函数。
2. **沉浸开发（约 1.2 小时）**：
   - 编写代码、运行单元测试、观察终端输出或 Token 消耗。
3. **极简收尾（3 分钟）**：
   - **只有**在遇到卡了 15 分钟以上的典型 Bug 或模型诡异行为时，才在 `notes.md` 中随手记 1~2 行（格式参考附录 C.1）；没遇到坑就不记。
   - 执行 `git commit -m "完成: xxx功能"`。

## 六、附录 A · 技术选型与依赖规划

| 类别 | 选用方案 | 核心理由 |
|---|---|---|
| **运行环境** | Python 3.12+ (conda 独立环境) | 生态兼容最好，开发阻力最小 |
| **类型检查** | `mypy` | 强制关键数据模型与函数标明类型，杜绝类型隐患 |
| **模型调用** | `langchain-core` + 官方集成包（`langchain-deepseek` 等） | 统一的消息与工具接口抽象 |
| **检索组件** | 阶段 1~2: `rank_bm25` 纯关键词；阶段 3+: `chromadb` 或 `lancedb` 轻量向量库 | 循序渐进，从无向量对比到有向量对比 |
| **代码解析** | Python 标准库 `ast` | 按函数与类精准切块，无需第三方重型依赖 |
| **工作流编排** | 阶段 1~3: 原生 Python 循环；阶段 4~6: `langgraph` 状态图 | 先体会手写的痛点，再享受框架的红利 |
| **日志与工具** | `loguru` + `pydantic` + `pytest` | 现代 Python 开发标配 |
