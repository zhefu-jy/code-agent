## 一、这个项目是什么

> **一个能给出「带证据链、可决策」答案的个人工程助手。**

形态上是一套东西，不是两套：

```
┌─ 一个入口 · 一套答案格式 · 一套评分 ──────────────────┐
│  数据源层：  代码索引   |   资料索引   |   提交历史      │
│  能力层：    检索与融合 |   冲突仲裁   |   上下文治理    │
│  输出层：    带出处与置信标注的答案 → 采纳/纠正回填 eval │
└────────────────────────────────────────────────────────┘
```

**边界（这条决定了你该往哪投时间）：**

| 问题层次 | 例子 | 谁的地盘 |
|---|---|---|
| 在哪（where） | 这个类在哪个文件 | ❌ IDE 已做得很好 |
| 是什么（what） | 这段逻辑做了什么 | ❌ IDE / 补全已做得很好 |
| **为什么（why）** | **订单超时为什么是 30 分钟** | ✅ **本项目** |
| **能不能改（can I）** | **改它牵连谁、有什么约束** | ✅ **本项目** |
| **对不对得上（consistent）** | **文档说 A，实现里是 A 吗** | ✅ **本项目** |

四字概括价值定位：**跨源、解释、沉淀。**

**定位提醒：这是台学习机器，不是交付系统。** 每个阶段只主攻一个能力，不许跳 ——
学习型项目最大的诱惑是"我全都要"，结果每样做一半、每样都没踩到底。

## 二、为什么选这个场景

学习型项目的选题标准跟商业项目不同，不看商业价值，看三条：

| 标准 | 说明 |
|---|---|
| **能长大** | 有持续新增的数据；问题会越来越复杂（今天问"在哪"，半年后问"为什么这么设计"） |
| **对错可自动判定** | 否则建不了 eval，**学习反馈就断了** |
| **能自然逼出多项能力** | 单一能力练不到东西 |

"代码库 + 技术资料助手"三条全中，且最强的理由是第二条：
**答案引用哪个文件、第几行，可以代码自动校验是否真实存在** —— 这是最稀缺的属性，eval 天生成立。
另外你每天都在产生新代码和新笔记，数据不用刻意维护；代码检索本身也比文档检索难得多。

**北极星场景（只选 1 个，别贪）：**

| 优先级 | 场景 | 为什么 | 出雏形 |
|---|---|---|---|
| **主** | 接手陌生模块时的理解助手 | 最高频、最痛、天生需要跨源推理 | 阶段 3 见效，阶段 4 完整 |
| 辅 | 变更前的调用方与约束排查 | 高频、对错明确（含"能不能改"的判断） | 阶段 4–6，**主场景跑顺了再加** |

## 三、练什么：Agent 工程能力地图（4 层 13 项）

**分水岭在状态层。** 教程覆盖的是上两层，而"agent 工程师"和"会调 API 的人"的分界线画在第三层。

### 基础层 · 能说话

| 能力 | 什么时候撞上 | 常见坑 | 算学会了 |
|---|---|---|---|
| 模型调用 | 第一天 | API key 写死；不做超时重试 | 换 provider 只改配置 |
| Prompt 管理 | 第一次要改 prompt | prompt 散落在代码字符串里，改个错别字要发版 | 独立存放、有版本号、可回滚 |
| 结构化输出 | 需要模型返回可解析数据 | 用正则抠 JSON，模型一换就崩 | 强制 schema，解析失败有兜底 |

### 交互层 · 能做事

| 能力 | 什么时候撞上 | 常见坑 | 算学会了 |
|---|---|---|---|
| 工具调用 | 第一次让模型查外部数据 | 工具做得太通用（一个 `query(sql)` 打天下）；返回 500 行 JSON | 窄而语义明确；返回值精简且带失败提示 |
| 检索 RAG | 资料超出上下文窗口 | 分块粒度拍脑袋；只用向量不做关键词混检 | 能说清为什么这么分块，并用数据验证过 |
| 循环与退出 | 让模型自主多步执行 | 无最大步数熔断；反复调同一个工具 | 有步数上限、死循环检测、降级路径 |

### 状态层 · 能应变 ★分水岭

| 能力 | 什么时候撞上 | 常见坑 | 算学会了 |
|---|---|---|---|
| 上下文工程 | 对话超过 10 轮 | 全量历史塞进去，token 爆炸且中间信息读不到 | 能主动决定每步塞什么、扔什么、压什么 |
| 记忆分层 | 需要跨会话记住 | 把记忆当聊天记录存，越存越乱 | 区分 working / episodic / semantic 三层 |
| 流程编排 | 流程有分支和并行 | 过度编排，把该让模型判断的地方也写死 | 知道哪些该写死、哪些该放权 |
| 中断与协同 | 出现写操作 | 没有审批，模型直接改了数据 | 高风险动作能挂起、等人确认、恢复且幂等 |

### 工程层 · 能活下来

| 能力 | 什么时候撞上 | 常见坑 | 算学会了 |
|---|---|---|---|
| 评测体系 | 想验证"改得好不好"的那一刻 | 靠感觉判断优化效果 | 有黄金集，一条命令跑出分数变化 |
| 可观测与成本 | 第一次收到账单 | 只知道总额，不知道哪个环节烧的 | 每步都能看到 token、耗时、成本 |
| 安全与权限 | 工具能力变强之后 | 把所有工具都给模型，包括写接口 | 工具分级授权，写操作有审计 |

### 两条贯穿始终的原则

- **workflow-first**：用确定的状态机管住流程，只在需要判断处让模型发挥。
  **多 agent 是陷阱** —— 写操作必须保持单线程，子 agent 只贡献判断、不直接改共享状态。
- **eval 是感官，不是工程规范**：商业项目没 eval 是亏钱，**学习项目没 eval 是白学** ——
  踩了坑你也判断不出自己爬出来了没有。

## 四、最终形态：三个数据源 + 交叉验证

### 4.1 三个源各自贡献什么

同一个问题，三个源给出不同层次的信息，缺一层答案就不完整。

| 数据源 | 回答什么 | 典型内容 | 可靠性 |
|---|---|---|---|
| **① 代码仓库** | 现在**是什么** | 源码、注释、配置、SQL、接口定义 | 事实本身 |
| **② 提交历史** | 何时变、为何变 | commit message、PR、issue、review 讨论 | 意图线索 |
| **③ 技术资料** | **为什么**、约束来自哪 | 内部设计文档、字段口径说明、运维手册、故障复盘、厂商对接说明、**锁定版本**的官方文档 | 权威依据 |

**一个具体例子 —— 问："订单超时为什么是 30 分钟？"**

| 来源 | 给出的证据 | 单独能回答吗 |
|---|---|---|
| 代码 | `OrderTimeoutService` 里常量 `30 * 60_000` | ❌ 只知道是 30，不知道能不能改 |
| 提交历史 | 2024-03 由 15 改成 30，message 写"对齐支付侧超时" | ⚠️ 看到方向，不知具体约束 |
| 技术资料 | 支付网关对接说明写明"支付侧超时 30 分钟" | ⚠️ 缺少与实现的对齐验证 |
| **三源融合** | 30 是**支付侧约束的映射**，不是业务取值；改它必须同步支付侧 | ✅ **可追溯、可决策** |

**这就是"技术资料"最本质的体现：它是让回答从"陈述事实"升级为"可决策"的那一层。**

**技术资料源具体包含什么：**

- **内部资料**（网上搜不到，价值最高）：内部 wiki、接口文档、表结构与字段口径、设计文档与评审记录、
  运维手册、**故障复盘**、你自己的笔记与坑日志
- **外部资料**（**必须绑定版本才可用**）：项目实际使用的框架/中间件/SDK 官方文档、
  对应版本的 release notes 与 breaking change、依赖库的 issue/changelog

> 外部资料不带版本标签，技术资料库价值接近于零 —— 它会稳定地给你"看起来正确但编译不过"的答案。

### 4.2 一致性审计：资料源存在的最硬理由

**"用资料 + 代码互相验证"的准确含义是：用两个互相独立的来源做交叉比对，把不一致暴露出来。**
这个能力的正式名字是一致性审计（consistency audit）。资料源的价值不是"多一份检索结果"，
而是"**有一个可以互相比对的独立来源**"。

|  | 代码里有实现 | 代码里没有 |
|---|---|---|
| **资料有约定** | 一致 —— 可直接采用，置信最高 | **★ 口径不一致** —— 文档过期，或实现漏做 |
| **资料无约定** | 隐形知识 —— 做对了但没人记，值得回写 | 盲区 —— 两源都未覆盖，需人工确认 |

**只有右上角那一格是真正的产出。**

- "一致"只是顺利回答，没有新信息
- "隐形知识"是文档缺口，顺手回写即可
- "盲区"是覆盖问题，靠扩充数据源解决
- **右上那格产出的不是答案，是「发现」** —— 你在被动接需求之外，第一次主动挖出问题：
  文档过期？实现漏做（真 bug）？配置与实际不符？

这一格把工具从"问答"升级为"发现"，而且产出可累积成资产（不一致清单）。

### 4.3 验证的上限：五级证据阶梯

**必须提前建立的预期：两个源一致，不等于正确。**
它们可能共享同一个错误前提（文档和实现都基于一个 2019 年的假设）—— 这叫**同源偏差**。

| 级别 | 证据 | 能得出什么 | 谁能提供 |
|---|---|---|---|
| 1 | 单一来源 | "据我看到的是这样" | agent |
| 2 | 代码 + 资料一致 | "实现与约定对得上" | agent |
| 3 | 加上提交历史 | "为什么变成这样、谁改的" | agent |
| 4 | 加上运行事实（日志、监控、测试） | "实际跑起来确实如此" | agent（要接生产数据源，**先不做**） |
| 5 | **人的判断** | 最终裁决 | **只有你** |

**由此推出的一条硬性产品约束：**

> **输出形态必须是「证据 + 推理 + 置信标注」，不是结论。**

- 每个结论挂出处（代码给文件+行号，资料给段落+时间，历史给 commit id）
- 标注证据等级（单源 / 双源 / 三源）与不确定项
- 不一致时**两个都报**，说明各自依据、指出哪个更可能过时，而不是挑一个顺眼的说

**为什么是硬性的**：一旦它只给结论，你就会开始盲信它 ——
盲信一个会犯错的系统，比没有这个系统更糟，因为你失去了怀疑的能力。

### 4.4 实体对齐：审计的前提（所以审计放阶段 6）

要判断"一致 / 不一致"，系统必须先认出这三个东西**是同一个实体**：

| 位置 | 形态 |
|---|---|
| 代码 | `private static final long ORDER_TIMEOUT_MS = 30 * 60_000;` |
| 文档 | "订单超时时间为 30 分钟" |
| 配置 | `order.timeout=1800` |

**同一个业务含义，三种形态，两种单位，零显式关联。**

没有实体对齐，审计只能做字符串匹配，误报率高到没法用；有了它，你顺手得到知识图谱的雏形，
后面所有能力都会变强。它没有标准答案，必须靠在真实项目里反复调 —— 这正是学习型项目要的东西。

**所以：阶段 1–5 老老实实做检索、问答、上下文与记忆。**
阶段 3 挂上资料源后，可以在答案里**顺带标注**"本条结论有/无资料佐证"（零成本初阶版），
但**不要承诺"一致性检查"这个功能**。

### 4.5 资料治理：比代码难的地方

| 问题 | 表现 | 原则 |
|---|---|---|
| **时效** | 一份 2023 年的文档，今天还成立吗 | 每份资料带最后确认时间；超阈值时答案主动提示"可能已过期" |
| **版本绑定** | 这份资料对应哪个技术栈版本 | 入库强制打版本标签；检索按项目实际版本过滤 |
| **冲突仲裁** | 文档写 A，代码里是 B，谁是真的 | **代码是当前事实，文档是当初意图。** 明确输出"文档已与实现不一致"，不许含糊地两个都报 |
| **可信度分层** | 论坛博客 vs 官方文档 | 排序权重：官方文档 > 内部设计文档 > 公开博客；答案中标注来源等级 |
| **失效检测** | 文档引用的类/方法已不存在 | 引用校验时顺带做存在性检查，失败即标记为可疑资料 |

**"冲突仲裁"是本项目最有价值的学习点之一** —— 它逼你思考一个纯 agent 的问题：
**多个证据源互相矛盾时，怎么让模型给出诚实且可决策的答案，而不是拼凑一个看起来完整的答案。**

### 4.6 审计的 eval 怎么建（这块能力的独门价值）

一致性审计有个**极其罕见的属性：它的对错可以算精确率与召回率。**
绝大多数 agent 场景你根本说不清"准确率"是什么（写篇周报，什么叫对？）但审计类任务不一样。

**建 ground truth 的方法：**

1. 手工挑 **20–30 个**你熟悉的业务点（订单超时、库存扣减、退款状态机……）
2. 逐个手工核对代码与资料，**人工判定**是否一致 —— 这是标注集
3. 让系统跑一遍，输出它的"不一致清单"
4. 对答案

| 指标 | 定义 | 低了会怎样 |
|---|---|---|
| **精确率** | 系统报出的不一致中，真不一致的比例 | 误报多 → 你会嫌它吵 → 然后不用它 |
| **召回率** | 人工标注的不一致中，被系统发现的比例 | 漏报多 → 你以为没事，其实有事 |

**两个都要看，单看一个没有意义。** 提高召回必然降精确，这个取舍是**本项目的核心调参对象**，
也是"人和 agent 如何分工"的真实训练。

它是整个项目里**唯一能量化精确率/召回率的场景**，也是你面试时最有力的一段话：

> 我做了个一致性审计，精确率 78%、召回率 61%。我选择偏向高精确（宁少报），
> 因为误报会让人直接关掉这个功能。后来把阈值调整，精确率降到 70% 换来召回率 82%，原因是……

（在能说出这句话之前，别急着写简历上的 agent 项目经历。）

## 五、演进路线（七阶段）

> 铁律：每个阶段只主攻一个能力。

| 阶段 | 加什么 | 对应能力 | 验收 | 会踩的坑 |
|---|---|---|---|---|
| **① 能说话** | 单轮问答 + 模型抽象层 + token 记账 | 基础层三项 | 能连续问 10 个问题；每次调用打印 token；换模型只改配置 | 以为这就叫 agent 了 |
| **② 装尺子** | `eval/cases/` + 30 条案例 + 一条命令跑分 | 评测体系（最小版） | 一条命令跑完并输出"通过 N 条"+ 基线数字 | **跳过它** —— 后面每次优化都无法验证，等于白做 |
| **③ 能查资料 ★** | 混合检索 + 挂第二个数据源 + 引用溯源 | 检索 RAG | 答案必给文件路径与行号；引用的文件真实存在 | 分块粒度拍脑袋，效果还不如 grep；中文短文本召回不稳 |
| **④ 自己决定查什么** | 检索工具化 + 多步循环 + 最大步数熔断 | 工具调用 + 循环退出 | 同一问题，模型能自己决定查几次、查什么 | 反复调同一工具、过早停止、被错误返回带偏 |
| **⑤ 扛长会话 ★** | 上下文工程 + 记忆分层 | 上下文工程 + 记忆分层 | 对话 50 轮后单次 token 不随轮数线性增长 | 上下文爆炸、成本飙升、中间信息读不到。**很多人在这里放弃** |
| **⑥ 按流程走** | 状态机编排 + 并行（`asyncio`）+ 中断恢复 + **一致性审计** | 流程编排 + 中断协同 | 流程可配置（加场景不改核心代码）；高风险动作会挂起等人确认 | 过度编排，把该让模型判断的地方也写死 |
| **⑦ 证明它行** | 一键回归 + 全链路 trace + 失败回放 + **冲突仲裁可解释** | 评测（完整版）+ 可观测 | 一次运行看到每步的输入/输出/工具/token；失败案例能完整重放 | 全量评测拖到现在才建，成本已经很高 |

**③ 和 ⑤ 是两个分水岭。** ③ 是"单源 → 多源"，你要处理的不是"再多一个索引"，而是
**不同源的分块策略完全不同**（代码有语法结构可切、文档无结构）、**证据怎么排序融合**、
**冲突时如何取舍** —— 比阶段 1–2 难一个量级，也正是最值得踩的坑。

## 六、明确不做

- [ ] 不做通用代码搜索 —— IDE 已经很好
- [ ] 不做**脱离版本**的通用语法 / API 问答 —— 通用 AI 已经很好
- [ ] 不做自动改代码、自动提交 —— 风险高，且不是学习重点
- [ ] 不做多用户、团队协作 —— **单用户原则**：第二个使用者会立刻拖进权限/隔离/合规，把你从"学 agent"变成"做平台"
- [ ] 不做全语言支持 —— 先只覆盖主力语言 + Markdown
- [ ] **不做实时增量索引** —— 前几阶段一律用"定时全量"这个最笨的办法
- [ ] **不做独立于代码助手的第二套系统** —— 资料源必须共用同一套检索 / 评测 / trace 底座
- [ ] 不做多 agent
- [ ] **不为"将来企业化"提前抽象**（多租户、权限模型、配置化抽象层）
- [ ] 不优化性能 —— **除非 eval 数字显示它影响效果**
- [ ] 不做前端 —— 命令行到 W16 都够用
- [ ] 不因为"看到一个新框架"就换技术栈

**最后两条特别重要：**

- **不优化索引**：新人做这类系统最容易陷进数据工程泥潭（写爬虫、解析各种格式、搞增量索引），
  半年过去还在处理数据，一行 agent 逻辑都没写。
- **不为"可扩展"提前抽象**：这是**过早泛化**。代价很具体 ——
  你会花三个月设计一个抽象层，然后发现根本没人用过它，**包括你自己**。

## 七、怎么判断它有没有价值

### 直接收益

1. **接手陌生模块**：从"翻半小时没头绪"变成"十分钟拿到带出处的解答"
2. **"这个能不能改"的判断**：不再靠猜和问人，而是看到约束来自哪里
3. **版本对齐**：照抄网上最新版答案导致编译不过的情况基本消失
4. **变更前排查调用方**：不用手动 grep 多个仓库
5. **排查时能翻到历史同类故障**：故障复盘不再沉睡在文件夹里
6. **避免重复踩坑**：坑日志可检索，不再"这个我好像遇到过"

### 间接收益（可能比直接收益更大）

1. **为了建索引，你会被迫系统性地读一遍自己维护的项目。** 很多开发对自己的系统只有碎片理解 ——
   这个副作用本身就是巨大的能力提升。
2. **你会第一次认真整理自己的资料。** 散落的 wiki、文档、笔记被迫结构化。
3. 项目本身成为转型作品集 —— 一个能讲清"为什么这么设计、踩了什么坑、数据怎么变好"的项目，
   比十篇学习笔记有用。
4. 学到的能力全部通用，换框架、换模型都还在。

### 风险与对策

| 风险 | 对策 |
|---|---|
| 做成一周只打开一次的玩具 | 北极星场景必须满足"每周 ≥3 次" |
| 文档源拖慢进度，卡在解析和分块 | 阶段 3 只接**一种**格式（先 Markdown），其余往后放 |
| 资料过期导致答案错误 | 阶段 7 的资料治理不是可选项；在那之前答案必须显示来源与时间 |
| 贪多，每样做一半 | 一次只做主场景，做透再扩 |
| 陷进索引与数据工程 | 前几阶段用最笨的全量方案，不优化 |
| 效果全凭感觉，不知道有没有进步 | 阶段 2 就建立最小 eval |

（月度自检的四问在《安排.md》附录 C.4，此处不重复。）

## 附录 A · 被修正过的 7 个判断

**留着是为了防止你按旧结论走。**一个方案的可靠性，取决于它被修正过多少次。

| # | 原判断 | 修正后 |
|---|---|---|
| 1 | 做 Agent 必须转 Python | **作为能力判断，它不成立** —— 应用层 Java 同样能做，而且"能把 agent 接进企业系统"的 Java 人反而是稀缺项。**但作为本项目的学习路径，Python 更优**：你看过的教程、敲过的案例、要读的源码全在 Python，用 Java 重写一遍等于把已有优势清零。**已定：本项目用 Python 实现。** |
| 2 | M0 按"交付系统"写 | 太重。学习型项目的 M0 只需定四件事：选能长大的场景、只定阶段 1 边界、建 `eval/cases/`、勾选想学的能力项。**其余让需求在开发中长出来** |
| 3 | 技术资料是代码的附注 | 错了。资料是**一等数据源** —— 含"为什么"的证据链、锁定版本查询、内部资料、资料治理 |
| 4 | 不做 API 用法问答 | 说过头了。该让给 IDE 的是**脱离版本**的通用问答；**锁定版本**的用法与兼容性判断只有你能做 —— 日常项目锁在 Spring Boot 2.7 而全网答案都是 3.x，本项目锁在某个 LangChain 版本而教程都是更新的版本，两种情况都照抄不过 |
| 5 | "验证" = 确认回答正确 | 实为**一致性审计**：用两个独立来源交叉比对，暴露不一致。**产出的是「发现」，不是「答案」** |
| 6 | 两个源一致 = 可信 | 有上限，可能**同源偏差**。五级证据阶梯的顶端只能是**人的判断** —— 由此推出硬约束：输出必须是"证据 + 推理 + 置信标注" |
| 7 | 用 Python = 放弃 Java 的积累 | **两件事。** 三年 Java 没浪费，只是换了作用位置：分层、接口抽象、状态管理、幂等与恢复这些思路语言无关，**直接用在设计上**（见《安排.md》附录 A 两条纪律）；语法层面的差异反而是最容易补的。真正的分工是 —— **Python 是这个领域的通用语言，Java 是企业落地的第二把武器**，两者不冲突 |

第 3 条和第 6 条是被追问出来的，第 7 条是本次追加的。**这个习惯（核对结论有没有兑现它声称的范围）用在项目上就是 eval 的思路。**

## 附录 B · 将来往企业级知识库迁移

**先纠正定义：企业级 ≠ 技术更先进。** 企业级 = **能被别人用、能被别人维护、出事有人负责。**
技术只占一小部分，带走的是**能力不是代码**。

### 可迁移性三层

| 层 | 内容 | 怎么对待 |
|---|---|---|
| **① 直接复用** | 证据链与出处设计、一致性审计、评测闭环（精确率/召回率）、上下文治理、冲突仲裁规则、trace 与成本记账 | **你练的核心，能带走** |
| **② 必须重建，但不产生新知识** | 索引与性能、增量同步、高可用部署、多源接入工程化、监控告警 | 工程量，有多少资源干多少活 —— **别当学习目标** |
| **③ 全新领域，与 agent 技术无关** | 权限与知识边界、内容生命周期、无 ground truth、冷启动、合规留痕、组织归属（**政治**） | 要重学，而且不靠写代码学 |

### 企业知识库的真实死因（不是你猜的那个）

| 死因 | 表现 | 常见（无效）技术应对 |
|---|---|---|
| 权限与知识边界没设计 | 越权泄漏一条敏感信息，项目当天叫停 | 优化检索排序 |
| 内容无人维护 | 三个月后文档全过期，答案开始害人 | 换更强的模型 |
| 没有评测 | 效果无法证明，预算被砍 | 做一个更炫的 demo |
| 冷启动失败 | 库里没东西没人用；没人用就没人补 | 继续调 chunk size |
| 组织政治 | 结论动了某个部门的蛋糕 | 无关技术 |

**技术投入九成花在"更好的检索和模型"上，而左列的死因一个都没解决** ——
这就是大量企业知识库"上线即巅峰、三个月无人问津"的机制。

### 你的位置：顺序是反的，但反得对

```
常规路径：先做检索 → 再做权限 → 补个前端 → 最后想"效果怎么衡量"（来不及了）
你的路径：先装尺子 → 再建证据链 → 练一致性审计 → 最后才是规模与权限
```

**"可信"这件事一旦延后，就永远补不上** —— 它不是功能，是整个系统形态的约束。

所以你的定位应该是：**"我不是做过企业知识库的人，我是知道怎么让知识库的答案变可信的人。"**

### 什么时候可以跨（三个条件，缺一不可）

1. 在个人项目里**跑通过一次完整评测闭环**（有基线、有分数变化、能说清每个变化的原因）
2. **踩过实体对齐与冲突仲裁的坑**（知道它们有多脏，知道"误报率比漏报率更致命"这类取舍从哪来）
3. 公司里有一个**真实需求 + 一个愿意负责的人** —— 不是你想做，是**有人需要**

**第 3 条最容易忽略，也最致命。** 企业知识库成败八成在组织、不在技术。
顺路建议：与其跳槽去接企业知识库，不如先在现公司找**一个小场景**试（一个团队、一个系统的文档 + 代码），
你的角色是"懂评测与证据链那个人"，不是"接 RAG 的人"。

### 现在唯一值得做的准备（一天的活）

**原则：只做接口留余量，不做功能提前实现。**

| ✅ 可以做（零成本） | ❌ 绝对不要做 |
|---|---|
| 检索层按**数据源**抽象（本就是阶段 3 要做的事） | 多租户架构 |
| "当前用户"作为参数传入，值是常量 | 权限模型与角色体系 |
| 答案格式里预留**来源等级**字段 | 为"通用"而做的配置化抽象层 |
| trace 里记录**数据源标识** | 接入第二个用户 |

分界线：**没有真实需求的东西，一律不实现。**
