## 四、异常用例深度剖析：Case 022（假阴性现象）

* **用例题目**：`ReviewReport` 是如何使用 Pydantic 的 `Field` 约束 `score` 分数在 0 到 100 之间，并且如何嵌套包含 `ReviewIssue` 列表的？
* **大盘表现**：大盘全跑时判定为 ❌ FAIL，但单题重放 `--case 022` 时判定为 **✅ PASS**。
* **深层根因定位**：
  1. 模型在回答中其实给出了极其详尽且 100% 正确的解答，命中期望符号（`ReviewReport`, `ReviewIssue`, `score`, `ge=0`, `le=100`），并附带 6 处真实合法引用。
  2. 但在大模型生成的末尾，模型严谨地附加了一句免责说明：
     > *“参考代码片段中未展示 with_structured_output 的内部实现细节，因此无法说明其如何具体执行 Pydantic 校验，此部分**无依据**。”*
  3. 判卷脚本中的 `has_no_evidence()` 正则在全局扫描到了“无依据”三个字，触发了拒答判定，从而判定为 `真实功能被模型判定为“无依据”`（这是典型的**自指元语言引发的判卷器假阴性 False Negative**）。
  4. 实际功能与模型能力完全达标，后续将在判卷逻辑中优化对“局部补充说明无依据”与“整题拒答”的区分。

## 六、调优总结与工程结论

1. **量化结论**：将滑动窗口切块尺寸由 `chunk_size=40, overlap=10` 调整为 `chunk_size=60, overlap=20` 后，**综合通关率由 84.0% 提升至 96.0%（提升 12.0%）**。
2. **权衡代价 (Trade-off)**：单题平均 Token 消耗从 `1,409 tok` 增加到 `1,811 tok`（增加了约 `28.5%`），这是因为切块容量增大导致注入上下文的背景代码变多。在可接受的预算成本内，换取了 12% 的准确率提升，**投入产出比极高**。
3. **架构启示**：调整物理行数切块是基于 BM25 检索阶段的高性价比优化手段；但要从根本上消除跨函数/跨类截断与假阴性，仍需在阶段三接入 **基于 Python AST 的语法边界切块**。
